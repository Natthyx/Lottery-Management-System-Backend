# Test environment (run against the fixed code)

**Every number in this suite is "local, single machine".** The load generator (k6), the app,
Postgres and Redis all ran on one laptop and competed for the same 8 cores and 8 GB of RAM.
Traffic went from k6 on macOS through Docker Desktop's port forwarding into a Linux VM. The numbers
describe this setup only. They are not production capacity figures.

Raw capture (generated by `run.sh`, secrets redacted): [env/environment_raw.txt](env/environment_raw.txt).
The machine, OS, Docker, Postgres, Redis and k6 versions are identical to the baseline run
([../baseline/results/ENVIRONMENT.md](../baseline/results/ENVIRONMENT.md)).

## How the app ran

Exactly as `docker-compose.yml` configures it: connected as the least-privilege role `lottery_app`
(confirmed in [phase0/db_roles_and_privileges.txt](phase0/db_roles_and_privileges.txt): `lottery_app` holds the app's
connections, is not a superuser and owns nothing), migrations run as the owner via `MIGRATION_DATABASE_URL`,
`LOCK_TTL=5s`, `LOCK_WAIT_TIMEOUT=10s`, pool 25/5, `MAX_WINNERS=100`, `TRUSTED_PROXIES` empty.

## Port cool-down (harness change made during this run)

Docker Desktop's VM-side port forwarder opens a new connection to the container for every client connection. With only
10,536 ephemeral ports and a 60 s TIME_WAIT, back-to-back contention runs exhausted the range twice during this run.
Docker's VM logged `connect: cannot assign requested address`, and clients saw EOF; the app never received those requests.
Details and evidence are in [superseded/README.md](superseded/README.md). From L3 on, `run_k6` waits before each k6 run until the
VM has fewer than 2,000 sockets in TIME_WAIT. 21 of 34 runs waited, 517 s in total ([cooldown.log](cooldown.log)). L2 and L2u
ran before this change and had no transport errors.
