# Superseded outputs (kept as evidence, not used for headline numbers)

## l3_first_attempt/

First full run of L3. The **retry** variants (`dup5_retry_*`) had a harness bug: the
duplicates path in `k6/l2_hot_event.js` re-sent busy requests with **no backoff** (the
single-booking path had 5-25 ms jitter; this one did not). With 200 VUs x 5 parallel
requests spinning on one event, many users used up all 200 attempts with only "busy"
answers and ended up with zero bookings (e.g. 150/200 and 696/1000 users got exactly one
booking; see `sql_run*.txt`). No user ever got more than one booking.

This is a client bug, so the "exactly one booking per user" FAIL is not a server
defect. It does show a real server property: the Redis lock is try-once with no queue,
so an aggressive client can be starved indefinitely (FINDINGS F4). The `dup5_noretry_*`
variants were not affected but were re-run anyway with the rest of L3.

Fix: same jittered backoff as the single path plus a `st_gave_up_after_max_attempts`
counter. L3 was re-run in full; see `../l3/`.

## l5_first_attempt/

The algorithm-level files are valid but were regenerated by the re-run. `fairness-api`
aborted on its first request that got no HTTP response (`PUT /events/536/close: EOF`,
see `run_log_excerpt.txt`). The event was still `open` afterwards, so the request never

now retries transport errors in an idempotency-safe way and prints how many it retried.
